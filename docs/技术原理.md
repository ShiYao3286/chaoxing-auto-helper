### 为什么每个 frame 都注入一份

`manifest.json` 里 `content_scripts.all_frames = true`，每个 iframe 都会跑一份 `inject.js`。

**这是必须的** —— 题目在第四层 iframe 里，从顶层跨域查 DOM 会遇到问题；而且各框架的滚动容器、视频元素都只在自己文档里能操作。

### 怎么避免重复执行

如果每份实例都去抢视频、抢答题、抢翻页，会打架。所以采用**就近处理**原则：

| 职责 | 谁做 |
|---|---|
| 视频 / 文档 / 测验 | 自己文档里有，就自己处理 |
| 「下一节」翻页 | **只有顶层** |
| 悬浮面板 | **只有顶层** |

顶层翻页前会向后台问一句「还有别的 frame 在忙吗」，确认都闲下来才翻页，避免在视频还在播时就跳走。

### 状态汇总

每个 frame 通过 `frame:status` 消息上报自己的状态，后台按 `tabId + frameId` 存一份，面板显示最新最忙的那条。

## 二、刷课实现

### 视频

```js
v.muted = true;
v.playbackRate = 倍速;
v.play();
```

要点：

- **videojs 兼容**：优先调 `player.playbackRate()`，没有就设 `v.playbackRate`
- **持续纠正**：很多播放器每秒把倍速偷偷改回 1x，所以主循环每轮都检查一遍
- **防切屏暂停**：拦截 `visibilitychange` / `blur` / `mouseleave`，并改写 `document.hidden`

```js
doc.addEventListener('visibilitychange', e => e.stopImmediatePropagation(), true);
Object.defineProperty(doc, 'hidden', { get: () => false });
```

### 任务点完成检测（v1.2.0 新增）

这是刷课的核心：**必须先确认任务点真的完成，才能翻页。**

#### 四级校验

代码里 `isCurrentChapterDone()` 按顺序检查：

```js
① #_studystate        学习通自己维护的全局状态（最权威）
② 当前树节点           .icon_Completed / .jobUnfinishCount
③ #jobhint            本节课待完成计数
④ 视频任务点标记       aria-label="任务点已完成"
```

#### ① `#_studystate`（最可靠）

页面里藏着一个学习通自己的状态：

```html
<input type="hidden" id="_studystate"
       value="{nextChapterId:1210130560,unfinishCount:93}">
```

| 字段 | 含义 |
|------|------|
| `nextChapterId` | 平台认为下一个该学的章节 |
| `unfinishCount` | 整个课程未完成总数 |

⚠️ 注意：value 是**伪 JSON**（键没引号），`JSON.parse` 会报错，必须正则提取。

#### ② 课程树节点

```html
<div class="posCatalog_select posCatalog_active" id="cur1210130560">
  <span class="posCatalog_name">三、毛泽东思想的历史地位（微课）</span>
  <input type="hidden" class="jobUnfinishCount" value="1">   ← 待完成数
  <span class="catalog_points_yi">1个待完成任务点</span>     ← 未完成标记
  <!-- 或 -->
  <span class="icon_Completed">已完成</span>                ← 已完成标记
</div>
```

#### ③ `#jobhint`

```html
<a id="jobhint" class="jobhint" style="display:none;">0</a>
```

`0` = 本节无待完成任务点。

#### ④ 视频任务点标记（关键修复）

**踩过的坑**：视频才播到 18%，平台已经标绿了。

原因：**学习通有每日限流**

```
今日视频任务点完成数已达上限，您可以观看视频，但无法完成任务点
今日视频观看时长已达上限，您可继续观看视频，但无法完成任务点
```

达到上限后平台不再累计，直接标完成。

**所以不能用进度判断，必须读平台标记**：

```html
<!-- 已完成 -->
<div class="ans-attach-ct videoContainer ans-job-finished">
  <div class="ans-job-icon ans-job-video ans-job-icon-clear"
       aria-label="任务点已完成">

<!-- 未完成 -->
<div class="ans-job-icon" aria-label="任务点未完成"></div>
```

读取优先级：

```js
function readVideoTaskState() {
  // ① aria-label 最直接
  for (const el of qAll('[class*="ans-job-icon"]')) {
    const aria = el.getAttribute('aria-label') || '';
    if (/任务点已完成/.test(aria)) return { done: true, source: 'aria-label' };
  }
  // ② 容器 class
  if (qAll('.ans-job-finished').length) return { done: true, source: 'ans-job-finished' };
  // ③ 明确未完成
  // ④ class 推断
  return null;   // 本页没有视频任务点
}
```

**进度判断降为兜底**，只在没有任何平台标记时才用。

### 章节内标签切换（v1.2.0 新增）

学习通一个章节常有多个标签：

```
1学习要点    ← 纯文字说明，不是任务点
2微课学习    ← 真正的视频/文档任务点在这里
3拓展阅读
```

#### 切换策略（用户选的方案 B）

**任务点在别的标签时，自动切过去做完再翻页。**

```
① 当前是纯文字标签，别处有内容型 → 切过去
② 当前内容型已做完，别处还有     → 切过去
③ 当前内容型没做完              → 原地等，别切走
④ 所有内容型都做完              → 检查任务点，过了就翻页
```

### 正确答案填充（v1.2.0 新增）

#### 三种题型选择器不同（重要）

| 题型 | `li` class | `span` class | `data` 值 |
|------|-----------|--------------|-----------|
| 多选题 | `before-after-checkbox` | `num_option_dx` | `A/B/C/D` |

#### 点击行为（实测）

```
多选题：点一次选中，再点一次取消   → 可累积（AB / ACD）
单选题：互斥，点新的自动取消旧的
判断题：和单选一样，点两次也会取消
```

**关键**：判断题点两次会取消！所以填充前必须**先清空所有已选中项**，再点目标。

```js
// 先清空
for (const o of q.options) {
  if (o.checked) { o.el.click(); await sleep(80); }
}
// 再点目标
for (const want of wants) {
  const target = q.options.find(o => o.value === want || o.letter === want);
  target.el.click();
  await sleep(100);
}
```

不能直接改 DOM，否则 `answer<qid>` 隐藏域不更新，提交时会报「未作答」。

## 三、字体反爬（核心）

### 问题

学习通对题干做了**字体混淆**。看这个例子：

```html
<p>忞忖忟命応首要忚忝忛？</p>
```

```css
@font-face {
  font-family: "puzzle-font";
  src: url("/font/xxx.ttf");
}
p { font-family: "puzzle-font"; }
```

页面上人眼看到的是「中国革命的首要问题是？」，但 `innerText` 拿到的是「忞忖忟命応首要忚忝忛？」。

**拿去问模型，模型会答非所问。**

### 破解步骤

```
① 抓 @font-face
   ↓
② 下载字体文件
   ↓
③ FontFace 注册，用它渲染混淆字符 → 位图
   ↓
④ 认出这个字体派生自哪款系统字体
   ↓
⑤ 用同源系统字体渲染候选字 → 位图
   ↓
⑥ 逐像素比对，取最相似的字
```

### 关键步骤：认出派生字体

这是决定成败的一步。

**实测数据**（同一批汉字，不同字体渲染）：

| 对比 | 余弦相似度 |
|---|---|
| 同字体渲染同一个字 | **1.0000** |
| SimHei vs 微软雅黑 | 0.4429 |
| SimHei vs SimSun | 0.7087 |
| 形近字「要」vs「耍」 | 0.941（SimHei） |
| 形近字「垄」vs「重」 | 0.867（SimHei） |

**跨字体差异（0.44）远大于形近字差异（0.94）**。

这意味着：如果随便挑个系统字体当参照，形近字会被字体差异淹没，必然混淆 —— 这正是早期版本把「要」认成「善」、「垄」认成「重」的原因。

**解决办法**：

反爬字体通常只改了「被混淆的那批码位」，其余字符原样保留。所以拿一批**绝不会被混淆的常用字**（的一是在不了有和…）分别用反爬字体和各个系统字体渲染，逐字比对：

- 派生字体 → 得分接近 1.0
- 其他字体 → 只有 0.4 左右

得分最高者即为基础字体。

```js
const PROBE_CHARS = '的一是在不了有和人这中大为上个国我以要他时来用们生到作地于出';

async function detectBaseFont(fontFam) {
  // 用反爬字体渲染探测字
  const mine = renderFeatures(fontFam, PROBE_CHARS.split(''));

  let best = null, bestScore = -1;
  for (const fam of pickSystemFonts()) {
    const ref = renderFeatures(fam, PROBE_CHARS.split(''));
    let sum = 0, n = 0;
    for (const [ch, v] of mine) {
      const rv = ref.get(ch);
      if (rv) { sum += cosine(v, rv); n++; }
    }
    const score = sum / n;
    if (score > bestScore) { bestScore = score; best = fam; }
  }
  return { family: best, score: bestScore, confident: bestScore > 0.90 };
}
```

### 字形特征提取

不是直接比对原始像素，而是先做**包围盒归一化**：

1. 找出墨迹的边界框
2. **保持宽高比**缩放到 28×28（不能拉伸！否则「问」的口字旁会被压扁，认成「门」）
3. 得到 784 维特征向量

```js
const scale = Math.max(bw, bh);       // 等比缩放
const padX = (scale - bw) / 2;        // 居中留白
const padY = (scale - bh) / 2;
```

> 踩过的坑：早期用「拉伸填满正方形」，结果「问」的口被压成了「门」。保持宽高比才对。

### 搜索策略

两级，兼顾速度和覆盖：

| 级别 | 字库 | 触发条件 |
|---|---|---|
| 一级 | ~2700 常用字（GB2312 一级 + 思政专业词汇） | 总是先跑 |
| 二级 | CJK 基本区 2 万字 | 一级得分低于阈值才跑，且限制批次 |

同源字体下，一级命中基本就是 1.0 分，直接采信；二级只在「字体被整体替换、认不出派生字体」时才用。

### 性能

批量渲染：所有字一次画到同一张画布（32 列网格），只 `getImageData` 一次，再切片。比逐字 `createCanvas` + `getImageData` 快约 30 倍。

实测：2700 字建库约 0.3 秒，单段文本解码约 0.5 秒。

## 四、截图解题

### 为什么不直接整屏截图

学习通是四层 iframe，整屏会把侧边栏、播放器、导航栏全截进来，视觉模型会被干扰。

### 做法

```
① 算出题目区域的精确矩形（getBoundingClientRect）
   ↓
② 后台 chrome.tabs.captureVisibleTab 截可见区域
   ↓
③ OffscreenCanvas 裁剪到该矩形
```

**踩坑**：`captureVisibleTab` 的第一个参数是 **windowId**，不是 tabId。传 tabId 会报 `No window with id: xxx`。

**踩坑**：Service Worker 里 `fetch(dataURL)` 不可靠，要手动 base64 解码成 `Uint8Array` 再建 Blob。

### 长题目分屏

题目比屏幕高时，裁剪会被自动收缩，导致漏题。所以：

```
截图 → 检查是否被裁剪 → 是则向下滚动一屏 → 再截
```

最多截 `maxShots` 张（默认 3），拼成一条消息里的多张图发给视觉模型。

### 降级方案

截图彻底不可用（后台休眠、页面不可见等）时，退回**把题目文字重绘成 canvas**。

虽然丢了原始排版，但视觉模型主要看文字内容，一样能解。这个降级路径在字体解码失败时特别有用 —— 因为解码后的文字已经是对的，重绘出来视觉模型能直接读懂。

## 五、脚本与模型的双向判断

用户要求「模型和脚本共同判断何时该用截图」。

### 脚本侧

```js
function assessTextReliability(scraped) {
  const reasons = [];

  // 1. 字体解码置信度低
  // 2. 题干过短
  // 3. 生僻字比例 > 15%（疑似还是乱码）
  // 4. 仍含已知混淆字符（忞忖忟命…）
  // 5. 单选/多选选项少于 2 个

  return { reliable: reasons.length === 0, reasons };
}
```

### 模型侧

视觉模型的提示词里强制要求每题返回 `confidence`：

```json
{
  "answers": [{ "num": 1, "answer": ["B"], "confidence": 1.0 }],
  "uncertain": false,
  "note": ""
}
```

`confidence < 0.6` 或 `uncertain: true` → 判定不可靠。

### 决策

```js
const wantVision = visionOn && (
  mode === 'always' ||        // 强制截图
  !assess.reliable            // 文本不可靠
);
```

### 安全设计

即使 `autoSubmit` 开着，只要视觉模型标了不确定，**仍然跳过提交**：

```js
const canSubmit = cfg.quiz.autoSubmit && !(visionMeta && visionMeta.uncertain);
```

理由：截图解题本来就比文本答题更容易出错，出错时自动交卷等于直接锁死分数。

## 七、任务队列（v1.3.0，搜题酱模型）

> v1.2.0 是"看当前页面图标 → 判断 → 行动"。v1.3.0 改成"先清点 → 排队 → 逐项做"。
> 这套结构来自对大学搜题酱 v1.17.5 的静态分析，详见 [搜题酱架构剖析.md](搜题酱架构剖析.md)。

### 为什么必须改

| 老问题 | 根因 | 队列方案怎么解 |
|---|---|---|
| 面板永远没有任务点明细 | `.ans-job-icon` 只在 cards 帧（d1），顶层查不到；子帧上报的消息后台没接收方 | 顶层扫 d1 的 `contentDocument`（同源可读），自己就有全量清单 |
| 视频"绿了"却判定未完成 | 只看进度数学 | 队列里每项带平台标记（`aria-label` 优先） |
| 章节多标签时不知道先去哪 | 靠 `isContentTab(标题)` 猜 | 队列告诉你任务点具体在哪个 iframe |

### 任务目录

任务类型由 URL 决定，不是靠猜 DOM：

```js
// /ananas/modules/<name> → rawType
const extractCxRawTaskType = (src) => {
  let path = src;
  try { path = new URL(src, location.href).pathname; } catch {}
  const m = path.match(/\/ananas\/modules\/([^/?#]+)/);
  return m ? m[1].toLowerCase() : '';
};
```

| rawType | 归到 | 我们支持 |
|---|---|---|
| `video` | video | ✅ 播放 |
| `audio` | audio | ✅ 播放 |
| `pdf` | pdf | ✅ 翻页 |
| `work` | work | ✅ 答题 |
| `zt/topicAttachment`（展开时） | pack | ✅ 当测验 |
| `zt/topicAttachment`（未展开） | pack | ⏭ 跳过 |
| `insertbbs` / `live` / 其它 | unknown | ⏭ 跳过，不阻塞 |

**不支持的类型不阻塞翻页**：标 `supported:false`，面板显示 `⏭` 删除线，队列判定时直接跳过。

### 扫描

在 d1（cards 帧）的 document 里扫：

| 对象 | 判定 |
|---|---|
| `iframe` | `src` 含 `/ananas/modules/` 或 `/ananas/dialog/ballchart`，且父级不是 `.cmd-autoblockquote` |
| `.blockquote-wrap` | 折叠块，各算一个任务 |
| 作业包 | `src` 含 `/ananas/modules/zt/topicAttachment` 且 `.pack-btn` 文字为「展开」→ `type:pack` |

**完成状态只信平台标记**：

```js
aria-label = "任务点已完成"  → true
aria-label = "任务点未完成"  → false
容器 class 含 ans-job-finished  → true
图标 class 含 ans-job-icon-clear → true
以上都拿不到  → null（未知，不算完成）
```

`null` 是关键设计：**拿不准就不算完成**，宁可可重复做，也不能漏做。

### 配对任务卡

从 iframe 逐层上溯，找第一个"只含 1 个任务点图标"的祖先：

```js
function closestTaskCard(node) {
  let cur = node.parentElement;
  for (let i = 0; i < 8 && cur; i++) {
    const icons = cur.querySelectorAll('[class*="ans-job-icon"]');
    if (icons && icons.length === 1) return cur;   // 就是这个卡
    if (icons && icons.length > 1) break;          // 到列表层了，不能再上
    cur = cur.parentElement;
  }
  return node.closest('.ans-attach-ct, ...');      // 兜底
}
```

直接 `closest('.ans-attach-ct')` 不可靠——实测 DOM 不一定有这层 class；
太高的祖先会把整页图标算进来，状态就串位了。

### 队列决策

```
有 frame 在忙 → 等
「还有任务点未完成」弹窗 → 处理
整门课完成（#prevNextFocusNext 被隐藏）→ 🎓 停
队列未做完且本章未完成：
    当前是纯文字标签 → 切到有任务点的标签
    当前队列做完了   → 先下滑确认没漏
    还有未做的       → 切到未试过的内容标签
队列做完 → 翻页
```

**两个防死循环的设计**：

1. `tabTried` 记录试过的标签。否则两个"已完成"的内容标签会互相切来切去（ping-pong）。
2. 队列项本身有 `done` 状态，做完的不会重做。

### 路由代际

学习通是 SPA，切章节/切标签时旧异步结果可能写回新页面。

| 层 | 实现 | 作用 |
|---|---|---|
| 指纹 | `routeFingerprint()` = `{href, mainIframeSrc, mainDocumentHref}` | 三字段全等才算同一路由。只看 href 会漏掉"标签切换但 URL 没变" |
| 代际 | `routeEpoch` + `isStale(epoch)` | 异步动作前抓 epoch，回来时变了就丢弃结果 |
| 章节 | `chapterChanged()` 比对 chapterId | 章节变了重置 `tabTried`/`docDone`/`quizSingle` |

任何"切标签 / 提交"这类长动作，都是 **抓 epoch → 动作 → 回来先查 isStale**。

## 八、提交安全网（v1.3.0）

> 原则：**没把握就不交**。失误是一次成绩，暂存只是一次点击。

### 为什么需要

v1.2.0 是"填完就交"。但填了 ≠ 填对了：

- 选项点下去了，平台却没认（隐藏域没变）
- 题型不支持（简答/论述），填了但看不出来
- 字体解码错了，答案本身是错的

### flags 模型

```js
workSafe = {
  total:      题目总数,
  done:       实际填进去几题,
  safe:       核对通过几题,
  unsafeReason: 第一条不安全原因
}
canSubmit = autoSubmit && total > 0 && safe === total
```

`unsafeReason` 保留**第一条**（和搜题酱一致），后面的不覆盖，避免原因被淹没。

### "safe" 怎么判

| 题型 | safe 条件 | 依据 |
|---|---|---|
| 单选 / 判断 | 隐藏域 `#answer<qid>` 的值 === 期望答案 | 平台认了才算填进去 |
| 多选 | 隐藏域排序后相等，或实际勾选数 === 期望字母数 | 同上 |
| 填空 | 写进去的每段都能在 textarea / iframe body / `.InpDIV` 里找到 | 三处都试，任一处找到即可 |
| 简答/论述/其它 | — | 无从核对 → `safe:false` |

**`safe:false` 不等于失败**：答案是填进去了，只是没把握。

### 三种结局

| 条件 | 动作 | 提示 |
|---|---|---|
| `canSubmit` | `doSubmitQuiz()` | 显示得分 |
| `wantSubmit && !canSubmit` | `doTmpSave()` 暂存 | ⚠ N 题未核对通过，未自动提交，已暂存答案，请自查后手动提交 |
| 没开自动提交 | 只填不交 | 提示已填写 |

### 提交弹窗状态机

```
点主提交按钮（先 removeAttribute('href')）
   ↓
等 ≤8s #workpop 真的可见（尺寸≥2px + computedStyle，不能只看 querySelector）
   ↓
#popcontent 含「未做完 / 未完成 / 还有题目」
   → 点 #popno 取消，返回 {ok:false, cancelled:true}
   ↓ 否则
点 #popok
   ↓
#workpopFocus 含「未达到及格线」
   → 点 #popno，不硬交
   ↓ 否则
读分数 .dividerCon .achievement i
```

**两个必须注意的坑**：

1. **弹窗常驻 DOM**：`#workpop` 一直是 `display:none`，直接 `querySelector` 会误判"弹窗已出现"。
   → 必须 `reallyVisible()`（尺寸 + computedStyle）。
2. **确认按钮找错对象**：主提交按钮文字也是「提交」，全局兜底搜索会把它当成弹窗确认按钮，连点两次。
   → `findPopupConfirmBtn()` **只在弹窗容器内**找。

### 暂存

```js
// 各窗口循环 → 先展开菜单 → 再点保存
点击 '.ZY_sub.clearfix'          // 展开菜单
点击 '.btnSave.workBtnIndex'     // 保存（removeAttribute('href') 后再点）
```

## 九、宿主抽象层（v1.4.0）

> **一句话**：刷课/答题逻辑写一遍，套两个宿主，产出扩展和油猴脚本两个形态。

### 为什么要有这一层

刷课/答题逻辑有 4000 行。如果为油猴脚本再写一遍：

- 两份必然漂移（改了一个 bug，忘了改另一个）
- 测试要维护两套
- 用户报的问题无法复用排查经验

所以抽成三层：

```
core/     内核：默认配置、提示词、API 调用、JSON 解析   ← 零 chrome API
content/  逻辑：任务队列、任务点判定、提交安全网         ← 只调 Host.*
ui/       界面：面板、设置弹窗                           ← 只调 CSTheme
─────────────────────────────────────────────
host/     宿主：把上面三层需要的能力用各平台 API 实现
```

### 宿主接口（唯一契约）

内核通过 6 个方法跟外界打交道，两个宿主各自实现：

| 方法 | 语义 | 扩展实现 | 脚本实现 |
|---|---|---|---|
| `Host.send(type, payload)` | 发消息等回复 | `chrome.runtime.sendMessage` | 本地分发到 `core/api` |
| `Host.sendNoWait(type, payload)` | 发消息不等 | 同上（忽略 Promise） | 同上 |
| `Host.on(fn)` | 收消息 | `chrome.runtime.onMessage` | 跨帧总线订阅 |
| `Host.getCfg()` / `setCfg(p)` | 读写配置 | `chrome.storage.local` | `GM_getValue/SetValue` |
| `Host.getRunning()` / `setRunning(v)` | 运行态 | storage + `tabs.sendMessage` 广播 | GM 存储 + 总线广播 |
| `Host.openOptions()` | 打开设置 | `openOptionsPage()` | 页内弹窗 `CSSettings.open()` |

**关键设计**：`send` 保持「`type` 字符串 + payload 对象 + 返回 Promise」的消息形状不变。
所以迁移 inject.js 时是**纯机械替换**——把那 14 处 `chrome.runtime.sendMessage({type:...})`
换成 `Host.send('...', {...})`，逻辑一行没改。

### 传输层注入（第二个关键点）

`core/api.js` 不做网络请求，而是调注入的 `_transport`：

```js
// 内核：只声明「我要发一个请求」
const resp = await request({ method: 'POST', url, headers, body, timeout });

// 扩展：background.js 注入 Service Worker 的 fetch（绕开页面 CORS）
CS.api.setTransport(async ({ method, url, headers, body, timeout }) => {
  const resp = await fetch(url, { ... });
  return { ok: resp.ok, status: resp.status, text: await resp.text() };
});

// 脚本：host-userscript.js 注入 GM_xmlhttpRequest（同样绕 CORS）
CS.api.setTransport(httpRequest);
```

这样同一个 `callAnswerApi()` 在两个形态里跑，一行不改。

> ⚠️ **踩过的坑**：脚本宿主最初漏了 `setTransport`，
> 结果所有答题/视觉请求都抛「传输层未注入」，表现为功能全瘫。
> 这是两个宿主唯一必须各自做的初始化。

### 跨帧协调的两种实现

扩展有背景页可以用共享内存；油猴脚本没有，只能靠页面内的通道。

| 环节 | 扩展 | 脚本 |
|---|---|---|
| 拿 tabId | `sender.tab.id`（framework 给） | 顶层生成 uuid 写进 `<html data-cs-tabid>`，子帧同源读取 |
| 通道 | background 里的 `Map` | `BroadcastChannel('cs-bus-' + tabId)` |
| 帧标识 | `sender.frameId`（数字） | 顶层到当前帧的 iframe 序号链（`'0'` / `'1'` / `'0.1'`） |
| 心跳 | 每次 `frame:status` 上报 | 每 2 秒广播一次 peer 状态 |
| 兜底 | — | 跨域读不到 `window.top.document` → 单帧模式（各帧独立判断） |

为什么 tabId 要写在 DOM 属性上：**`<html>` 的属性跨世界共享**。
内容脚本的隔离世界看得到页面写的属性，页面也看得到脚本写的 ——
这是比 `postMessage` 更简单的同源帧间共享手段。

### 功能一致的验证方式

不是"看着一样"，而是同一批测试跑两个形态：

| 测试 | 跑在哪个形态 |
|---|---|
| `test-kernel-health.cjs` | 扩展（Service Worker + importScripts） |
| `test-userscript.cjs` | 脚本（产物注入 fake 页 + GM 桩） |
| `test-userscript-bus.cjs` | 脚本（真实双 iframe 页验证跨帧） |
| `test-build.cjs` | 脚本（产物静态校验，含"无 chrome 残留"） |

`test-build.cjs` 里有一条硬规矩：**除了宿主文件，任何源码出现 `chrome.*` 就构建失败**。
这条规则是防止未来有人图方便在逻辑层直接调扩展 API —— 那样脚本版会静默失效。

## 十、UI 设计令牌（v1.4.0）

### 三个界面，一套令牌

悬浮面板（两形态共用）、脚本设置弹窗、扩展设置页 —— 三处视觉必须一致，
所以颜色/圆角/间距/阴影集中写在 `src/ui/theme.js`：

```js
root.CSTheme = {
  color: {
    primary: '#2d6cdf',            // 主色
    primaryLight: '#4b8bf5',       // 渐变亮端
    ink: '#141414', ink2: '#626466', ink3: '#8b949e',
    line: '#f0f1f3', hover: '#f7f8fa', disabled: '#b9babd',
    ok: '#2da44e', warn: '#b26a00', off: '#8b949e',   // 语义色
    msgOkFg/msgOkBg, msgErrFg/msgErrBg, ...           // 消息条
  },
  grad: { brand: 'linear-gradient(135deg,#4b8bf5,#2d6cdf)' },
  radius: { card: 12, sm: 8, pill: 14 },
  size: { panel: 300, btnHeight: 32, switchW: 40, switchH: 24 },
  shadow: '0 8px 24px rgba(15,23,42,.10)'
};
```

`cssVars(selector)` 把它渲染成 CSS 变量块，注入样式表开头，正文规则全部 `var(--cs-*)`。

### 设计来源与边界

结构和控件风格借鉴了大学搜题酱（12px 卡片圆角、左标签右控件、Element 风格开关、32px 按钮），
但**配色/渐变/语义色是自有的**，且不复用它的任何代码或图标资产：

| 沿用（通用设计参数） | 自有（保持识别度） |
|---|---|
| 12px 卡片圆角、柔和阴影 | 主色 `#2d6cdf`（它用 `#2655fe`） |
| 左标签 · 右控件布局 | 渐变 135°（它用 270°） |
| Element 风格开关 40×24 | **语义色保留绿橙灰**（它整个面板只用蓝） |
| 32px 按钮高度、300px 面板宽 | 按钮带图标 `▶ 开始` / `■ 停止`（它纯文字） |

**语义色为什么不跟它**：搜题酱整个面板一个蓝色系，扫一眼分不清"做完了还是正在做"。
我们用绿 ✓ / 橙 ⚠ / 灰划线，一屏能看清进度 —— 这是现有实现的优势，不能为了像而丢掉。

### 硬约束（构建时校验）

`build/build-userscript.cjs` 会检查 `ui/*.js`（除 theme.js 外）源码里
**不得出现六位十六进制颜色**。想加新颜色必须先进 `theme.js`。

这条规则防止「改一个界面忘了改另一个」，也避免三个月后没人知道 `#fff0f0` 是什么。

## 十一、已知限制

| 限制 | 说明 |
|---|---|
| 视频倍速上限 | 受浏览器限制，实际最高 16x，建议 ≤2.0 |
| 跨域 iframe | 非同源 iframe 无法穿透，此时该 frame 的功能不可用 |
| 字体认不出派生 | 退化为多字体投票 + 骨架归一化，精度下降 |
| 视觉模型必备图片能力 | `deepseek-chat` 这类纯文本模型不能用 |
| Service Worker 休眠 | MV3 特性，靠消息自动唤醒 |
| **每日任务点上限** | 学习通平台限制，非 bug。命中后扩展主动停止 |
| **提交确认弹窗** | 未真实验证，已加通用「确定/确认」兜底点击 |
| **填空题提交识别** | 直接写 `textarea.value`，需真实提交验证是否被采纳 |
| **子帧调度延迟** | 测验帧的循环依赖顶层广播，偶有 1-2 轮延迟 |
| **跨域课程队列** | 读不到 d1 `contentDocument` 时退化回标签逻辑，此时无队列清单 |
| **讨论/直播类任务** | `bbsReply`/`bbsTopic`/`bbsTopicList`/`live` 不支持，跳过不阻塞翻页 |
| **脚本版无真实截图** | 油猴脚本拿不到 `captureVisibleTab`，截图解题降级为文字重绘 |
| **脚本版不跨标签页** | 没有 background，运行状态只在本标签页内有效 |
| **脚本版需授权域名** | 首次调 API 要用户在油猴弹窗点「总是允许」，否则请求发不出去 |


### 每日限流说明

学习通会按天限制任务点完成数：

```
今日视频任务点完成数已达上限，您可以观看视频，但无法完成任务点
今日视频观看时长已达上限，您可继续观看视频，但无法完成任务点
```

表现出来就是：**视频才播十几 %，任务点就标绿了**。

这不是脚本的问题，是平台行为。脚本检测到后会主动停止：

```
⏸ 今日视频任务点已达上限，今天无法再完成任务点。已停止
```

第二天自动恢复。
